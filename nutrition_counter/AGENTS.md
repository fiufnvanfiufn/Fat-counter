# Инструкции для агентов

## Источники требований

Перед изменениями прочитайте:

1. `spec/product/product.md` — задача пользователя, сценарии, границы версии и критерии приёмки.
2. `spec/tech/architecture.md` — текущий стек, структура и технические ограничения.
3. `spec/tech/rag.md` — корпус, BM25, Gemini и ограничения режимов чата.
4. `README.md` — запуск проекта; `CHANGE_HISTORY.md` — история изменений.

Пустой или отсутствующий раздел спецификации не означает, что соответствующий компонент реализован. Отличайте текущее поведение от планов. При противоречии файлов с явным запросом пользователя следуйте запросу и синхронизируйте документацию.

## Порядок работы по SDD

1. Определите затрагиваемые требования и критерии приёмки.
2. Если меняются сценарий, границы версии, стек или архитектура, сначала актуализируйте соответствующий SDD, затем реализацию. При документировании уже выполненной работы сверяйте SDD с кодом.
3. Вносите изменения в рамках задачи. Сохраняйте пользовательские изменения в рабочем дереве.
4. Проверьте затронутые сценарии и команды запуска. Не представляйте непроведённые проверки как успешные.
5. Обновите README при изменении запуска или поведения и добавьте запись в CHANGE_HISTORY с датой, изменениями и результатами проверки.

## Технологии и ограничения

* Текущий интерфейс: HTML5, CSS3 и обычный браузерный JavaScript без фреймворков и сборки.
* Основной сервер: Python 3.10+, FastAPI, Pydantic, SQLite/aiosqlite. Раздаёт интерфейс и `/api/*`. Node.js `server.mjs` — устаревшая статическая раздача без рабочего API.
* Сохраняйте этот стек для изменений приложения. Добавляйте зависимости или сборку только при обоснованной необходимости задачи; фиксируйте причину и запуск в техническом SDD и README.
* Текущий этап включает BM25 и Gemini по `spec/tech/rag.md`. Отделяйте генерацию от поиска без ключа; не выдавайте старые mock-данные за публикации.
* Дневник, профиль и избранное уже используют SQLite. Сохраняйте их API и данные при миграциях; функции вне требований не добавляйте.
* Ключ провайдера читается только сервером. Учебное исключение по явному запросу владельца: заполненный `backend/.env` включается в передаваемый проект и разрешён для Git; владелец подтвердил доступ к квоте для всех читателей репозитория. Не выводите значение и не включайте его в HTML, ответы API или логи. Другие секреты не добавляйте. Пример формата без ключа — `.env.example`.
* Корпус содержит локальные пересказы официальных публикаций. Новые записи должны иметь проверенный URL, издателя, стабильный ID и дату проверки конспекта. Не добавляйте вымышленные источники и не представляйте конспект как полный текст оригинала.
* Учебный benchmark: 30 документов `D01`–`D30`, 10 ответных вопросов с эталоном/релевантными ID и 5 ловушек без ответа в корпусе. Эталоны находятся только в `benchmark/`, не используются приложением при поиске или генерации. После получения ответа разрешена отдельная структурная диагностика E1/E5/«О» по совпавшему вопросу; смысловые E2–E6 не назначайте без проверки. Не подгоняйте ответы приложения под список вопросов. Отчёт офлайн-поиска не выдавайте за проверку качества LLM или отказов.
* Benchmark v1 воспроизводится на `benchmark/corpus-v1.json` с весом заголовка 0. Рабочий корпус и BM25 с весом 2 развиваются отдельно; для сравнений задавайте `--corpus`, `--title-weight` и новый `--output`. Не перезаписывайте архивные результаты при исправлениях обычных запросов.
* База знаний — каталог всех канонических статей через `/api/knowledge`, избранное — отдельный раздел. Не подменяйте один другим и проверяйте обе кнопки каталога.
* Записи дневника передавайте модели только по явному `scope=diary` после действия пользователя с пояснением передачи. Снимок формируется сервером; обычный чат его не получает. Не добавляйте имя, возраст, вес пользователя или ограничения, не объявляйте все записи полным текущим днём и не рассчитывайте медицинские нормы.
* Не включайте биллинг и не переключайте провайдера/модель на платный вариант автоматически. Тестируйте интеграцию подменным HTTP-транспортом; живые запросы требуют доступного пользовательского ключа.
* Пользовательский текст вставляйте через `textContent` или эквивалентное безопасное создание DOM, а не через `innerHTML`.
* Сохраняйте русскоязычный интерфейс, адаптивность, управление клавиатурой и поддержку `prefers-reduced-motion`.
* Публикуйте только файлы фронтенда; для старого Node.js-сервера сохраняйте явный список разрешённых файлов. Не открывайте HTTP-доступ ко всему репозиторию или серверным файлам конфигурации, включая учебный `.env`.

## Запуск и проверка

Из корня репозитория `Fat-counter`:

```powershell
.\nutrition_counter\backend\.venv\Scripts\python.exe -m uvicorn main:app --app-dir nutrition_counter/backend --host 127.0.0.1 --port 8000
.\nutrition_counter\backend\.venv\Scripts\python.exe -m unittest discover -s nutrition_counter/backend/tests -v
node --test nutrition_counter/frontend/tests/chat.test.mjs
node --check nutrition_counter/frontend/app.js
.\nutrition_counter\backend\.venv\Scripts\python.exe nutrition_counter/benchmark/run.py
git diff --check
```

Установка окружения описана в README. Сервер запускайте в отдельном терминале: он работает до `Ctrl+C`. Адрес — `http://localhost:8000`.

Проверяйте затронутые критерии продуктового SDD: режим без ключа, отсутствие контекста, атрибуцию, ошибки провайдера, повтор запроса и сброс во время загрузки. При изменении схемы БД проверяйте миграцию с сохранением избранного и пользовательских данных. Для интерфейса дополнительно проверяйте карточки, клавиатуру и узкий экран. Автоматизированные тесты не заменяют визуальную проверку; если браузер или живой Gemini недоступны, укажите границу проверки в отчёте.

Для каталога проверяйте обе точки входа, поиск, чтение и повтор загрузки. Для кнопки анализа проверяйте фактический серверный снимок и пустой дневник; проверяйте отсутствие личного контекста в обычном запросе. При локальной проверке используйте отдельную тестовую БД и свободный порт, если пользователь уже запустил свой сервер. Не останавливайте его процесс. Для применения изменений в пользовательском терминале поясните перезапуск backend и `Ctrl+F5`.

Для отдельного прогона benchmark с LLM добавьте `--live`: он расходует квоту. Отчёты и метрики оформляйте по `benchmark/README.md`. Качество эталонных ответов нельзя считать автоматически подтверждённым только по совпавшим ID источников или отказу модели.
