# Продуктовый SDD: Помощник по дневному контролю калорий

## Пользователь и задача
**Пользователь:** Человек, следящий за своим рационом, который хочет вести дневник питания и получать достоверную информацию о продуктах.
**Задача:** Получать ответы на вопросы о питании, вести дневник приёмов пищи (Завтрак, Обед, Ужин, Перекусы), отслеживать дневной калораж и сохранять полезные материалы.

## Основной сценарий
1. **Чат с ассистентом:** Пользователь вводит вопрос или выбирает подсказку, получает развернутый ответ и ссылки на проверенные источники.
2. **Дневник питания:** Пользователь добавляет блюда в разделы «Завтрак», «Обед», «Ужин» или «Перекусы», выбирая их из базы продуктов (`FOOD_DATASET`) или вводя вручную.
3. **Статистика нутриентов:** Система автоматически пересчитывает калории, белки, жиры и углеводы по записанным блюдам, показывая прогресс-бары выполнения целей.
4. **Избранное и профиль:** Пользователь может сохранять понравившиеся статьи в Избранное и задавать цели калорий и белка в Профиле.

## Проверяемые требования

* Под каждым ответом доступна разметка качества E1–E6 с расшифровкой кодов. Для совпавших вопросов benchmark после генерации автоматически проверяются E1 (нет релевантного документа в топ-3), E5 (ответ на ловушку) и корректный отказ «О». Остальные классы и смысловую верность оценивает проверяющий по эталону; отсутствие автоматически установленного кода не выдаётся за отсутствие ошибки. Сбой API отмечается отдельно и не считается E5 или корректным отказом.
* Интерфейс запускается локально без ошибок.
* Реализована навигация между разделами: Чат, Дневник и статистика, Избранное, Профиль и цели, База знаний.
* Дневник питания позволяет добавлять и удалять блюда по 4 приёмам пищи (Завтрак, Обед, Ужин, Перекусы).
* Поиск по базе продуктов (`FOOD_DATASET`) фильтрует доступные блюда в реальном времени.
* Введённые блюда, параметры профиля и избранное сохраняются на сервере в SQLite через REST API.
* Адаптивность и управление с клавиатуры сохранены.

## Этап RAG (2026-11-24)

* Чат использует BM25-поиск по локальным конспектам официальных статей и, при серверном ключе, Gemini. Заготовленные ответы удаляются из рабочего пути.
* Ответ сопровождается только найденными и процитированными источниками, ссылкой на оригинал и выдержками. Конспекты обозначаются как пересказы.
* Видны режимы Gemini + BM25, поиск без LLM, отсутствие материалов. Без ключа выводятся найденные выдержки, а не имитация генерации.
* Ошибки провайдера объясняются, вопрос можно повторить. Новый разговор отменяет запрос; устаревший ответ не появляется.
* В режиме Gemini вопрос и фрагменты передаются Google; интерфейс сообщает об этом. Дневник и профиль автоматически не передаются.
* Ключ задаётся только на сервере. Регистрация у провайдера, включение биллинга и оплата не выполняются приложением.
* Медицинские назначения и персональная диагностика не входят в задачу.

## Исправление пользовательских сценариев (2026-11-24)

* Обе кнопки «База знаний» открывают отдельный каталог всех 30 текущих документов, а не избранное. Доступны поиск по ID/заголовку/содержимому, чтение конспекта и оригинала, добавление в избранное; пустое избранное не скрывает корпус.
* Короткие тематические запросы (например, «белок») трактуются как просьба о кратком обзоре. На широкие вопросы можно дать подтверждённую часть ответа с ясным обозначением отсутствующих данных; для неподтверждённых точных фактов, диагнозов и назначений сохраняется отказ.
* Вопросы о сахаре различают верхний предел свободных сахаров и обязательную потребность, свободные сахара и сахар в цельных продуктах. Числа и общие риски добавляются только по проверенным источникам.
* Кнопка анализа рациона явно отправляет записанные блюда, их суммы калорий/БЖУ и заданные цели Gemini. Передача происходит только при действии пользователя и сопровождается видимой подписью. Обычный чат этих данных не получает.
* Пустой дневник даёт понятный ответ с предложением добавить блюда, не вызывает LLM и не придумывает рацион. Итоги относятся к записанным записям, без обещания анализа дня/недели при отсутствии фильтрации по датам.
* Исходный benchmark и отчёты сохраняются с замороженным корпусом v1; рабочий корпус и промпт можно улучшать без перезаписи результатов прошлого эксперимента.

## Учебный benchmark (2026-11-24)

* По заданию подготовлены заранее 30 документов с ID `D01`–`D30`, 10 обычных вопросов, релевантные документы и эталонные ответы, а также 5 вопросов-ловушек с ожидаемым отказом.
* Документы — самостоятельные краткие конспекты официальных публикаций. Исходный benchmark по умолчанию проверяется на замороженном `benchmark/corpus-v1.json`; текущий корпус приложения развивается отдельно и сравнивается явным отдельным прогоном. Вопросы и эталонные ответы не добавляются в индекс и не передаются LLM как подсказки.
* Ловушки проверяют отсутствие нужного факта даже при совпадении терминов питания, а не только полное отсутствие лексических совпадений.
* Если найденные фрагменты не отвечают на вопрос, LLM должна отказаться от содержательного ответа и не приписывать ответ источникам. BM25 сам по себе не определяет достаточность доказательств; без ключа показываются только найденные кандидаты.
* Отчёт явно разделяет офлайн-поиск, реально выполненную генерацию и ручную проверку по эталону. Недоступный живой Gemini отмечается как непроверенный.
* Для учебной передачи владелец явно выбрал включение серверного `backend/.env` в Git и предоставил ключ. Наличие файла само по себе не гарантирует доступность провайдера или остаток квоты.
