# Технический SDD: BM25 и RAG

## Разметка по эталонам после ответа

После генерации отдельный модуль сопоставляет точный текст вопроса с benchmark (нормализация регистра/пробелов/конечной пунктуации). Эталоны не участвуют в поиске или промпте. Для совпавших вопросов автоматически проверяются E1 (эталонный документ вне топ-3), E5 (содержательный ответ на ловушку) и «О» (отказ на ловушку). E2/E3/E4/E6 не выдаются за автоматически доказанные: необходима содержательная сверка. Неизвестный вопрос получает отметку о необходимости эталона. Диагностика возвращается в `diagnostic` и отображается под ответом.

При явном `answerable=false` заполненные моделью `items` и `sources` отбрасываются до проверки схемы. Пользователь видит только стандартный отказ, без этих советов/ссылок. Строка `"false"` вместо булева `false` по-прежнему отклоняется; ошибки JSON, сети и обрыв генерации не превращаются в корректный отказ.

## Диагностика провайдера (2026-11-28)

Ошибки Gemini возвращают безопасные `detail.code` и `detail.message`: отдельно лимит токенов, блокировка, пустой ответ, повреждённый JSON, несоответствие схеме и неизвестные источники. Неисправный результат зависимости возвращается как HTTP 424, недоступность как 503, квота как 429, таймаут как 504. Клиент показывает код вместе с пояснением. Сырые ответы модели, ключи и персональные данные в диагностику не включаются. Это технические коды, не оценка качества E1–E6.

## Текущее состояние на 2026-11-24

Вместо mock-чата реализована цепочка: вопрос → локальный BM25 → фрагменты конспектов → Gemini → ответ и источники. Используются существующие Python/FastAPI backend, SQLite и Vanilla JS. Node.js-сервер не предоставляет API и не запускает RAG. Без ключа работает самостоятельный режим поиска с выдержками. Ключ предоставлен владельцем; реальный ответ через Gemini 3.1 Flash-Lite получен. Ранее выбранная 3.5 Flash-Lite вернула 503 (перегрузка), поэтому модель для учебного запуска явно заменена; автоматического переключения нет.

### Корпус и поиск

* `backend/knowledge/articles.json` — 30 версионируемых русскоязычных пересказов официальных публикаций с ID `D01`–`D30`. Это локальные редакторские конспекты, а не полный текст оригинала; каждый содержит `id`, `title`, `category`, `description`, `publisher`, `url`, `updated_at`, `content`, `keywords`. `updated_at` — дата проверки конспекта, а не публикации исходной статьи. Старый ID первых 11 статей хранится в `legacy_id` для переноса избранного без удаления старых строк.
* При старте сервер проверяет корпус и строит индекс в памяти. Текст разбивается по абзацам с ограничением 180 слов; короткий конспект может составлять один фрагмент.
* Unicode-нормализация, нижний регистр, `ё → е`, выделение слов, стоп-слова и Snowball-стемминг русского/английского применяются одинаково к запросу и индексу. Для чередования в «белок / белком» дополнительно нормализуется основа `белок → белк`.
* BM25 вычисляется локально (`k1=1.5`, `b=0.75`, IDF `log(1 + (N-df+0.5)/(df+0.5))`). Индекс включает заголовок и ключи, модели передаются реальные фрагменты конспекта.
* В рабочей версии к основному score добавлен отдельный BM25-сигнал заголовка с весом `title_weight=2.0`, чтобы тема статьи не проигрывала случайному упоминанию в чужом тексте. `BM25Index(..., title_weight=0)` воспроизводит начальное ранжирование. Число кандидатов и запрет выдумывать факты не меняются.
* Возвращается до четырёх фрагментов, не более двух от одной статьи, с положительным score и совпадением значимого терма в тексте или заголовке. Лексическое совпадение не гарантирует достаточность источника.
* При отсутствии совпадений ответ имеет `mode=no_context`, без источников и без обращения к модели.

### Генерация

* Gemini Developer API, REST `generateContent`; модель по умолчанию `gemini-3.1-flash-lite`, переопределяется через `GEMINI_MODEL`. На дату проверки заявлен Free tier: [тарифы](https://aistudio.google.com/docs/pricing#gemini-3.1-flash-lite). Доступ зависит от [региона](https://aistudio.google.com/docs/available-regions) и квот проекта. Приложение не активирует биллинг и не переключается на платную модель; тариф самого ключа оно не определяет.
* Ключ `GEMINI_API_KEY` читается только из окружения или серверного `backend/.env` и не передаётся браузеру. Учебное исключение по подтверждённому выбору владельца: `.env` с предоставленным ключом включается в Git для передачи преподавателю. `.env.example` содержит только формат настроек.
* В режиме `general` модели отправляются только вопрос и найденные публичные фрагменты. Снимок дневника передаётся лишь при явном `scope=diary` после нажатия кнопки с пояснением передачи. На бесплатном тарифе Google может использовать запросы для улучшения продуктов — это обозначается в README и интерфейсе.
* Системная инструкция требует русского ответа только по контексту, запрещает выполнение внедрённых в документы/вопрос инструкций, выдуманные факты/URL и медицинские назначения. Промпт не гарантирует фактическую точность.
* Короткая тема, например «белок», означает просьбу об обзоре функций и источников. Для широкого составного вопроса разрешён полезный ответ на подтверждённую часть с явным указанием границы знаний. Это не разрешение заполнять пробелы: отсутствующие точные данные товара, персональные дозы, диагнозы и назначения по-прежнему требуют отказа. Каждый фактический пункт должен опираться на действительно использованный документ.
* JSON валидируется сервером. LLM возвращает `answerable`: при `true` нужны непустые `sources` только из переданных документов; при `false` нужны пустые `sources` и `items`. Неподдержанные ID отклоняются. Возвращаемые `passages` ограничены процитированными документами. При отказе приложение выводит стандартное объяснение `mode=no_context` без источников, фактический текст модели не показывается. Одних лексических совпадений недостаточно для ответа на ловушки.
* Без ключа работает `mode=retrieval`: точные выдержки конспектов с сообщением об отсутствии LLM. Ошибки существующего ключа, региона, квот, таймаутов, сети, блокировки или формата не маскируются заготовленным ответом; автоматических повторов нет.

### API и данные

`POST /api/chat`: `{ "question": "...", "scope": "general" }`, 1–2000 символов после удаления крайних пробелов. Поле `scope` по умолчанию `general`; допустим также `diary`. Ответ: прежние `intro`, `items`, `end`, `sources` плюс `mode` (`gemini`, `retrieval`, `no_context`), `model` (или null), `warning` (или null), `passages` (`source_id`, `chunk_id`, `title`, `text`, `url`, `score`) и необязательный `diary_summary`.

Для явного анализа дневника сервер сам получает записи из SQLite, а не доверяет переданным браузером итогам. В `PERSONAL_DIARY_JSON` входят последние 50 блюд (`meal`, `name`, `weight`, `cals`, `protein`, `fat`, `carbs`), число всех записей, суммы калорий/БЖУ по всем записям, положительные цели калорий и белка и `scope_note`. Имя, возраст, рост, вес пользователя и пищевые ограничения не включаются. Эти данные допускается обобщать и сравнивать с указанными целями; они не являются основанием рассчитать новую медицинскую норму. Дневник пока не фильтруется по датам и не гарантирует полный текущий день. `diary_summary` возвращает `record_count`, `totals`, `targets`, `scope_note` для проверки пользователем. При отсутствии записей LLM не вызывается.

`GET /api/knowledge?q=...` возвращает только документы текущего индекса `D01`–`D30` с данными `SourceRead`, независимо от избранного; `q` необязателен. Это источник отдельного каталога, тогда как `/api/sources` сохраняет совместимость с избранным и старым API.

`GET /api/chat/status`: `provider`, `configured` (наличие ключа, а не проверка работоспособности), `model`, `documents`, `chunks`; секреты отсутствуют. Одновременно допускается один запрос LLM на процесс, остальные получают 429; слот освобождается при ошибке/отмене. Общий таймаут генерации по умолчанию 30 секунд (`GEMINI_TIMEOUT_SECONDS`, допустимо 1–120). Отмена браузерного запроса обнаруживается сервером и отменяет ожидающий вызов; уже принятую Google обработку или расход квоты это не гарантирует отменить.

Корпус синхронизируется в SQLite с сохранением избранного. Источники получают `url`, `publisher`, `content`, `updated_at`. При первом добавлении нового ID отметка избранного переносится с `legacy_id`; последующие решения пользователя по новому ID не перезаписываются. Старые строки доступны по прямому API ID, но дубликаты переименованных статей скрыты из списка. Старые демонстрационные записи сохраняются ради избранного, исключаются из BM25 и обозначаются как материалы без подтверждённой публикации.

### Проверка

Тесты: релевантные запросы и словоформы, пустой/нерелевантный вопрос, атрибуция и запрет неизвестных источников, миграция SQLite, режим без ключа, ошибки и таймауты Gemini с подменным HTTP-транспортом, освобождение слота при отключении клиента. Frontend-тесты проверяют отмену, устаревшие ответы, повтор и безопасный вывод. Команды приведены в README.

Дополнительные регрессии: база знаний доступна из обеих кнопок и не зависит от избранного; поиск/чтение/сбой каталога; обычный чат не содержит личного снимка; `scope=diary` использует серверные значения и не включает личность пользователя; пустой дневник не вызывает модель. После расширения корпуса отдельно проверяются обычные вопросы о сахаре и краткая тема «белок», без подстановки готового ответа из теста.

В браузере проверяются режимы, ссылки/выдержки, ввод, сброс, мобильное меню и отсутствие горизонтального переполнения. Подменный транспорт проверяет обработку ответов/ошибок, а живой доступ проверяется отдельным вызовом с ключом. Валидация идентификаторов источников не доказывает, что каждое утверждение ответа подтверждено текстом; маленький лексический корпус ограничивает полноту поиска.

### Расширение корпуса

1. Добавьте запись в `backend/knowledge/articles.json` по существующей схеме: уникальный стабильный ID, HTTPS-ссылка на проверенную публикацию, издатель, краткий пересказ и ключевые слова.
2. Соблюдайте права на исходный материал. Не добавляйте полный текст без основания; явно обозначайте локальный пересказ в `description` и фиксируйте дату его проверки.
3. Добавьте проверку тематического запроса в `backend/tests/test_rag.py`, затем выполните тесты и перезапустите сервер. При старте пересобирается индекс и обновляются данные статей в SQLite; отметки избранного сохраняются.
4. При изменении контракта синхронизируйте продуктовый SDD, архитектуру, README и историю изменений.

### Учебная оценка

`benchmark/` содержит фиксированные 10 обычных вопросов с релевантными ID и эталонами и 5 ловушек с причиной отсутствия ответа. Эталоны не импортируются кодом RAG. Офлайн-прогон проверяет структуру корпуса и ранжирование BM25; генерация, содержательная точность и отказ LLM без реального вызова не оцениваются. Живой прогон выполняется отдельно с ключом и сохраняет фактические ответы, источники и режимы для ручного сопоставления с эталонами. Неуспехи не скрываются и не заменяются эталонными текстами.

Исходный корпус перед исправлениями обычных вопросов сохранён в `benchmark/corpus-v1.json`. Runner по умолчанию использует этот снимок и `--title-weight 0`; старые метрики относятся к нему. Для текущего приложения используйте `--corpus nutrition_counter/backend/knowledge/articles.json --title-weight 2 --output nutrition_counter/benchmark/results/current-offline`. Такой прогон сохраняется отдельно, без перезаписи исходных отчётов. В рабочем корпусе расширены D01, D03 и D08, а число документов и стабильные ID сохранены.

Первый зафиксированный прогон: Hit@4/Recall@4 = 100%, MRR@4 = 0.825. В полном живом прогоне получены 10 обычных ответов, 4/5 отказа на ловушках и одна ошибка провайдера (T04). Отдельный повтор T04 дал отказ; исходный отчёт не изменяется. Эти результаты относятся только к данному набору и не доказывают семантическую корректность всех утверждений модели. Команды, эталоны и отчёты — в [описании benchmark](../../benchmark/README.md).
