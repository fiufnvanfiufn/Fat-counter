# Технический SDD: архитектура

## Статус и назначение

На 2026-11-24 реализован интерактивный веб-интерфейс с чатом BM25 + Gemini, дневником приёмов пищи (Завтрак, Обед, Ужин, Перекусы), каталогом продуктов, статистикой калорий/БЖУ, избранным и профилем. Данные хранятся на сервере в SQLite и доступны через REST API. Чат без ключа возвращает найденные выдержки; с ключом — ответ Gemini по найденным конспектам или явный отказ при недостаточном контексте. С предоставленным владельцем ключом проверен настоящий ответ модели `gemini-3.1-flash-lite`.

Интерфейс содержит отдельный каталог базы знаний, не связанный с условием «добавлено в избранное». Явная кнопка анализа рациона использует серверный снимок дневника; обычный чат персональные записи не получает.

## Архитектура

```
┌──────────────┐       HTTP (fetch)       ┌──────────────────┐
│   Браузер    │ ◄──────────────────────► │  FastAPI (8000)   │
│  index.html  │   /api/profile           │   main.py         │
│  app.js      │   /api/meals             │   schemas.py      │
│  styles.css  │   /api/sources           │   database.py     │
└──────────────┘   /api/foods             └────────┬─────────┘
                   /api/chat                       │
                                                   ▼
                                           ┌──────────────┐
                                           │   SQLite DB   │
                                           │ fat_counter.db│
                                           └──────────────┘
```

FastAPI раздаёт статические файлы фронтенда (`/`) и предоставляет REST API (`/api/*`). При старте загружает и валидирует `knowledge/articles.json`, синхронизирует статьи с SQLite и строит BM25-индекс в памяти.

`GET /api/knowledge` возвращает только канонические документы текущего индекса, отсортированные по ID, с необязательным текстовым фильтром `q`. Состояния каталога — загрузка, готовый список, отсутствие совпадений и ошибка с повтором. Обе кнопки «База знаний» открывают этот экран; «Избранное» остаётся отдельным разделом.

Поток чата: браузер → `/api/chat` → `RagService` → BM25 → найденные фрагменты → Gemini при наличии ключа → валидация ответа и источников → браузер. Без ключа возвращаются выдержки; без совпадений — состояние `no_context` без обращения к Google. Модель также может вернуть `answerable=false`, когда лексические совпадения есть, а запрошенных фактов в контексте нет; сервер показывает отказ без источников и выдуманных пунктов. Подробные параметры, ограничения и контракт — в [RAG SDD](rag.md).

## Сохранение данных

Данные дневника питания, профиля, избранных статей и базы продуктов хранятся в серверной базе SQLite (`fat_counter.db`, путь переопределяется `FAT_COUNTER_DB`). При первом запуске база создаётся и заполняется начальными данными. `localStorage` для этих данных не используется.

Миграция таблицы источников добавляет `url`, `publisher`, `content`, `updated_at`. Статьи корпуса обновляются по стабильному ID без сброса избранного. При переходе к ID `D01`–`D30` поле `legacy_id` связывает первые одиннадцать документов с прежними ID и позволяет перенести закладки; последующий запуск не должен повторно восстанавливать снятую отметку. Старые демонстрационные записи сохраняются ради существующих закладок, но в BM25 не индексируются и обозначаются как материалы без подтверждённой публикации.

Корпус содержит 30 кратких локальных пересказов WHO, NHS, Harvard Nutrition Source, NIDDK и Food Standards Agency, а не полные оригинальные статьи. D01, D03 и D08 расширены для обычных вопросов об энергии, белке и сахаре. Индекс пересобирается при перезапуске. Текущий BM25 дополнительно учитывает совпадения заголовка с весом 2.0; значение 0 воспроизводит первоначальный вариант.

Учебный набор содержит 10 ответных вопросов и 5 ловушек; вопросы и эталоны отделены от индекса и промпта. Первоначальный корпус сохранён в `benchmark/corpus-v1.json`: runner по умолчанию проверяет его с весом заголовка 0. Сравнение текущего корпуса/веса сохраняется в отдельный отчёт и не перезаписывает старые результаты. Офлайн-прогон оценивает поиск, живой — дополнительно сохраняет ответы и проверяет отказ; содержательную полноту ответов оценивают вручную.

## Файловая структура backend

```
backend/
├── main.py            # FastAPI, REST API, жизненный цикл и раздача фронтенда
├── database.py        # Слой работы с SQLite (создание таблиц, seed, подключение)
├── schemas.py         # Pydantic-модели запросов и ответов
├── retrieval.py       # Проверка корпуса, разбиение, токенизация и BM25
├── rag.py             # Поиск, режимы ответа и контроль атрибуции
├── llm.py             # Асинхронный клиент Gemini и безопасные ошибки
├── config.py          # Чтение серверной конфигурации
├── knowledge/articles.json  # Локальные конспекты со ссылками на оригиналы
├── tests/             # unittest: retrieval, API, миграции и подменный Gemini
├── requirements.txt   # Зависимости Python
├── .env.example       # Пример настроек без API-ключа
├── .env               # Предоставленный ключ для учебной передачи, читается только сервером
├── .gitignore         # Игнорирование .venv/, __pycache__/, fat_counter.db; учебное исключение для .env
└── .venv/             # Виртуальное окружение (не в git)
```

## Запуск и границы

Основной сервер: `uvicorn main:app --app-dir nutrition_counter/backend --host 127.0.0.1 --port 8000` из подготовленного Python-окружения. Полные команды для Windows и Linux/macOS — в [README](../../README.md). Node.js нужен только для JS-проверок или устаревшей статической раздачи.

Во время выполнения ключ читает только сервер; браузер и API его не получают. В учебном комплекте `backend/.env` разрешён для Git по явному запросу владельца, поэтому ключ доступен читателям этой копии. Обычный запрос отправляет вопрос и публичные фрагменты. Только `scope=diary`, инициированный явной кнопкой с пояснением передачи, вызывает `database.get_diary_context()` и добавляет `PERSONAL_DIARY_JSON`. Он содержит последние 50 блюд, число всех записей, суммы калорий/БЖУ по всем записям и положительные заданные цели калорий/белка. Названия блюд и вес порций входят в записи; имя, возраст, рост, вес и пищевые ограничения пользователя не передаются. Пустой дневник обрабатывается без LLM. Поле `diary_summary` возвращает число записей, суммы, цели и границы снимка для отображения пользователю. Данные не объявляются автоматически итогами текущего дня.

Провайдерские ошибки не заменяются mock-ответом. Сервер допускает один активный вызов Gemini на процесс и освобождает слот при завершении, ошибке или отмене. Интерфейс использует `AbortController` и счётчик запросов, чтобы после сброса не появился устаревший ответ. Для применения обновлённого backend/корпуса пользователь перезапускает свой сервер, а для обновлённого JS выполняет `Ctrl+F5`.

Профиль и дневник пока относятся к одному локальному пользователю; авторизация и многопользовательская изоляция не реализованы. История дневника по датам и полноценная недельная статистика в этот этап не входят. Проверки, включая ограничения живого Gemini, фиксируются в CHANGE_HISTORY.
